# Kin watching GitHub with the owner's login (`node scripts/kin-model.ts github-events`)

**Rules.** Each thing on GitHub wakes an agent at most once, whether Kin read it on several looks or stopped halfway through one. On a PR's thread: once Kin has caught up, every teammate's PR and `/kin` either woke an agent or was stopped for the hour with a note; only a teammate's PR or `/kin` wakes an agent, and a stranger's `/kin` and the agent's own signed replies never do; at most one 👀 per thing; one "stopped for the hour" note per thread per hour. On a new issue that triage answers (a stranger's too, in a turn that may post one comment): Kin answers people at most three times after its first comment, one comment each (`RepliesCapped`); only a person's comment wakes a reply, never the agent's own or a bot's (`NoReplyToSelf`); issues wake at most ten agents an hour per repo (`RepoHourCapped`) and strangers at most ten an hour across the owner's repos (`OutsideHourCapped`).

| Switch rule | Checked |
| --- | --- |
| `OffNextLook` | A look that starts with triage off does not wake an agent for an issue. |
| `OffAtOnce` | Once triage is off, Kin claims no triage wake or comment, even for a look or turn already under way. |

**Harm guarded.** An agent answering itself in a loop, on a PR or an issue, or answering a bot; a stranger starting work with the owner's login, beyond one confined comment per new issue; a PR reviewed twice after a restart; a teammate's `/kin` lost because the server stopped mid-look or a busy look hit its cap; a thread spammed with notes; a flood of new issues waking agents past the hour; an issue answered after the owner said not to.
**Bound.** Each run watches one thread. A PR's: up to four things (the agent's replies included), one wake-up per look, two per thread in the hour, one stop anywhere (97,826 states, as before). Or one new issue: up to five things (the issue, comments by a person or a bot, the agent's comments), two looks at once, one hour's end, the switch turned off once, one stop anywhere; replies scaled to two (the code's three), the hour's ceilings to two per repo and one for strangers (the code's ten each). 325,978 states (97,826 of them the PR's). `--variants`: 16/16 caught.
**Fixed.**

1. `NoneLost`: (1) Two teammates write `/kin` on a thread. (2) Kin's look wakes an agent for the first and is at its cap. (3) The second was stored as handled and never woke anyone. Over the cap a trigger is now left for the next look, with the cursor held. Variant `skip-over-cap`.

**Model choices.** The cursor is an index into one thread; the code's is a time (`since_at`) read back five minutes, with the stored keys deciding. A look reads the thread as it is when it starts. On a PR the hour's end is left out: it only resets the counts the rules bound. On an issue: a position stands for a time ("after Kin's comment" is after its place); `seenTo` stands for the `seen:` rows, which every look writes for what it read, so they are always everything up to some comment; the two looks are the minute's poll and the webhook's `lookAt`, which share no lock, and each reads the switch, the history and the comments once, then claims at most one key (an issue's `triage` needs no comment of Kin's yet and a `triage_reply` needs one, so a look never has both), the claim and the look's `seen:` marks being one step (a stop between them only leaves comments to weigh again, whose key is stored). One issue stands for the repo's: the hour's ceilings are scaled below one issue's own triage and replies so one issue reaches them, and the hour's end is in because the replies' cap spans hours and the ceilings do not; the strangers' ceiling is scaled under the repo's so each is seen to hold by its own check. A comment's author is inside exactly when the issue's is (a stranger on a teammate's issue makes its reply outside through the same `!trigger.inside`). The thread's hour (5) is left out on an issue: triage alone wakes at most 1 + 3 there in an hour. The 👀 on an issue is not counted: it follows the wake as on a PR. An off refusal stores no comment receipt and can end with `Quiet`; other refused posts (`commentfail:`) store nothing the rules count and can be retried. `Post` checks the switch at Kin's receipt claim and represents an admitted comment GitHub takes; it does not split that claim from network delivery. Turning triage off does not recall a comment Kin already admitted. A post GitHub never answers is `Answer(FALSE)`: the comment is there and Kin never stores it.
**Left out.** Several threads and repos, the 6-hourly repo list, a review requested of the owner, failing checks, the label (each is one more trigger kind through the same `handle`), the reply the owner is told (the reply model), what the agent's turn may do (the session rule's tests; an inside triage turn may also comment with `gh` from its shell, which `RepliesCapped` does not count), and time: a trigger past a day is stored stale, and a handled row that woke no one is pruned after 30 days (`STALE_MS`, `prune`). On an issue: a `/kin` or the label on it (triage then steps aside, `starts`, which only removes wakes), a bot's or the agent's own new issue (`isBot`, `agentsOwn` on the author, in `githubTriggers.test.ts`), an issue opened before triage began, the App's coverage (`appOn`: unknown defers a stranger's triage, which only removes wakes), the switch turned on again (`triageFrom` moves to then, so earlier issues stay untriaged), the per-look cap (one key a look), and two hosts or a restored database, each of which can still post once (the review's finding 4: the model has one host and one database).
