# Kin rules and what enforces them

Each rule below is one Kin got wrong more than once. A check now refuses the mistake, so a brief or a review doesn't have to repeat it. Lint rules live in `oxlint-plugin-t3code/rules/kin-*.ts` and are switched on for Kin paths in `vite.config.ts`. `vp run check:changed` runs all of them, plus the branch checks.

Inside a file T3 owns, Kin adds only a hook: an import, one entry in a list, or one call to a Kin function. The branch checks fail a branch that adds more than 10 lines to an existing T3 file; Kin's own paths are listed in `scripts/kin-t3-footprint.json`, and new files, `routeTree.gen.ts` and `pnpm-lock.yaml` don't count. T3's test files do: Kin's cases for a T3 module go in a sibling `<name>.kin.test.ts`, which Kin owns, so they never conflict on a sync. Move the code into a Kin file, or, when it truly belongs in T3's file, say why in a commit: `T3-file: <file>: <why>`. An upstream sync passes: its merge commit carries `Sync-upstream:` (the sync steps in [KIN.md](../../KIN.md) write it), and only what the branch adds after that merge counts. A file Kin adds outside its folders goes on the list in the same branch.

Run `node scripts/kin-branch-checks.ts mine/kin` to run the branch checks on their own. It prints every `People-change:` line the branch carries, so whoever merges reads them without opening the commits. Given a ref without Kin's files, such as upstream's `main` that plain `check:changed` picks, they run against the closest Kin trunk (`kin`, `<remote>/kin`) and say so. On GitHub, the Kin workflow (`.github/workflows/kin.yml`) runs the branch checks and the models a change touches on every pull request to `kin` and every push to it.

## Judgment only

No check covers these. Decide them in review:

- Workers and local workers act as the owner himself (`isOwnerHimself`), not as any co-owner, because they run on his host.
- Goals are visible to the whole team by design (`goalsNow` takes no viewer).
- `pulse/senses/money.ts` decides when an invoice is overdue with its own chase grace; it doesn't use `owedInvoices`. Keep the two in step by hand.
- A client screen uses the device's zone for when things happened, since the device belongs to its viewer. Company due days use the owner's zone through `kinZonedDayStart`.
- A loose check-in shows "around" a time. `KinSchedules.isAround` decides which ones are loose.
- Every entry on a money list carries the list's private label, and Kin can't tell it from the owner's own (`ownLabelOff` in `work/teamView.ts`): a project's lead sees every invoice filed under their project, and the owner can't hide one invoice from that lead alone.
- Outside a project they lead, a teammate sees a money entry only when it is shared with the team and their Money place is on; there is no sharing one invoice with one person.
- A header count and the list under it come from separate SQL in a few places: the Work summary and the client page's owed counts. They use the same predicate, so a change to one must change the other.
