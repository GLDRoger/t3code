# Memory repo guard rails

Templates for the private memory repo (`kin-memory`). This public repo holds only the templates and the code they run; never copy memory into it. The design is in [Memory repo guard rails](../../../docs/kin/specs/triggers.md#memory-repo-guard-rails).

| File                  | Goes to                                     | What it does                                                                                           |
| --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `CODEOWNERS.template` | `.github/CODEOWNERS`                        | Gives `rules.md`, `decisions/`, `people/`, `objectives/` and `.github/` to the owner.                  |
| `memory-check.yml`    | `.github/workflows/memory-check.yml`        | The `memory-check` job: schema lint, then gitleaks, on every PR and every push to `main`.              |
| `gitleaks.toml`       | stays here; the workflow reads it from here | `KinSecretScan`'s rules in gitleaks form, generated by `apps/server/src/kin/memory/gitleaksConfig.ts`. |

## Install

1. Copy `CODEOWNERS.template` to `.github/CODEOWNERS` and replace `@OWNER` with the owner's GitHub login.
2. Copy `memory-check.yml` to `.github/workflows/` and set `T3CODE_REF` to a full `GLDRoger/t3code` commit SHA that contains this folder. The job fails until it is set.
3. Open both as one PR and check that `memory-check` passes.

To pick up new lint or scanner rules, bump `T3CODE_REF` in a reviewed PR. The lint code and the gitleaks config always come from that commit, never from the PR's own files, which the job reads only as data.

The ruleset on `main` (PRs required, code-owner review, `memory-check` required, no bypass for Kin's bot) comes in the TRIG-15 follow-up, after APPR-11.

## Cost

Each run checks out `t3code` at the pinned commit without `.repos/`, installs the server's dependencies with `vp install --frozen-lockfile --ignore-scripts --filter=t3...` and runs the lint with Node. The install dominates: 881 packages, which took 19 s from an empty store on a fast connection, so budget about a minute per run on a hosted runner, plus Vite+ and Node setup. Nothing is cached between runs, so a PR can't seed a cache the check later trusts. Gitleaks is a 7 MB release binary, checked against its sha256 before it runs, and scans the tree plus the new commits in seconds.

## Things to know

- GitHub runs a PR's own copy of this workflow, so a PR could rewrite the check. The `/.github/` line in `CODEOWNERS` is what stops that: such a PR needs the owner's review. An org ruleset that requires this workflow from a pinned ref would remove the gap; consider it with the ruleset.
- A `.gitleaksignore` anywhere in the memory repo fails the check, because gitleaks would honour it. `gitleaks:allow` comments are ignored.
- A false positive the owner allowed in `kin_secret_allow` still fails gitleaks, which has no allowlist. Reword the text; whether the owner may merge past the check is settled with the ruleset.
- Gitleaks matches the scanner's patterns but not its Unicode folding or wrapped-token joining; it adds its own decoding and covers every commit in the PR.
