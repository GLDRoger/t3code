# Memory repo guard rails

Templates for the private memory repo (`kin-memory`). This public repo holds only the templates and the code they run; never copy memory into it. The design is in [Memory repo guard rails](../../../docs/kin/specs/triggers.md#memory-repo-guard-rails).

| File                  | Goes to                                     | What it does                                                                                           |
| --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `CODEOWNERS.template` | `.github/CODEOWNERS`                        | Gives everything to the owner except the paths Kin writes alone.                                       |
| `memory-check.yml`    | `.github/workflows/memory-check.yml`        | The `memory-check` job: schema lint, then gitleaks, on every PR and every push to `main`.              |
| `gitleaks.toml`       | stays here; the workflow reads it from here | `KinSecretScan`'s rules in gitleaks form, generated by `apps/server/src/kin/memory/gitleaksConfig.ts`. |

## Install

1. Copy `CODEOWNERS.template` to `.github/CODEOWNERS` and replace `@OWNER` with the owner's GitHub login.
2. Copy `memory-check.yml` to `.github/workflows/` and set `T3CODE_REF` to a full `GLDRoger/t3code` commit SHA that contains this folder. The job fails until it is set. Confirm the commit is on `kin` or `main` (`git branch -r --contains <sha>`): GitHub serves commits from any fork PR under the repo's name, so an unmerged SHA could carry someone else's lint.
3. Open both as one PR and check that `memory-check` passes. It lints the whole merged tree, so files already on `main` count too: memory written before these guard rails may hold paths the lint now refuses (nested items, names with dots). Move or rename those in the same PR.

To pick up new lint or scanner rules, bump `T3CODE_REF` in a reviewed PR. The lint code and the gitleaks config always come from that commit, never from the PR's own files, which the job reads only as data.

`scripts/kin-rulesets.ts` applies the ruleset on `main` (PRs required, code-owner review, `memory-check` required, no bypass for Kin's bot) from `KIN_REPOS`, where the memory repo has `kind: "memory"`, which accepts this file's owner-less Kin lines. Kin's own writes then reach `main` as PRs from `kin/write/<agent>/<id>` branches that it merges itself, and changes to owner paths as `…-review` PRs it leaves for you. Each review PR's body and Kin's message name the commit Kin pushed; the deploy key can push to that branch, so close the PR if its head differs. Kin also closes it within a few minutes when its head moves, and closes any other `kin/write/*` PR no write is waiting on. That needs the Kin App installed on this repo and the repo in `KIN_GITHUB_REPOS`. Without the App, Kin refuses to write `main`; `KIN_MEMORY_DIRECT_PUSH=true` makes it push directly, which this ruleset rejects.

### The owner's own changes

The owner is the only code owner, and GitHub never lets an author approve their own PR, so a PR the owner opens on an owned path (a `T3CODE_REF` bump, a hand edit to `rules.md`) can never merge. Use the code repo's sync flow ([approvals spec, section 10](../../../docs/kin/specs/approvals.md#10-github-the-bot-app-the-owners-review-rulesets)) instead:

1. The owner pushes a branch with the change, using their own credential, never the Kin host's.
2. The bot adds one same-tree commit on top (`POST /git/commits` with the owner's tree and commit as its only parent, then the ref update) and opens the PR, after checking that `head^` is the SHA the owner pushed and `head^{tree}` is its tree.
3. The owner approves as code owner, which counts because the bot authored the PR, and squash-merges in the GitHub UI.

Nothing automates this yet: Kin has no code that adds the same-tree commit or opens the PR, for this repo or the code repo. When the diff touches `.github/workflows` (every `T3CODE_REF` bump does), check by hand that GitHub accepts the bot's same-tree commit, because the App has no Workflows permission. With `require_last_push_approval` off here, the bot opening the PR is what makes the approval count, so if GitHub refuses that commit, the bot can open the PR from the owner's head as it is.

### Workflow permissions

`memory-check` is pinned to the GitHub Actions App (15368), which trusts any Actions workflow in the repo, not just `memory-check.yml`. A workflow pushed to any branch could post a passing `memory-check` on another PR. The repo's read-only workflow-permissions setting doesn't stop this: anyone with write access, which includes the memory deploy key that agents can read, can raise a workflow's own `permissions:`. A ruleset `workflows` rule would close the gap, but it exists only in organization rulesets, and `GLDRoger` is a user account. So a passing `memory-check` alone is not trusted: before merging a PR, Kin checks that its head is the SHA Kin pushed and merges with `sha` pinned to it. It refuses unless a `pull_request` run of `.github/workflows/memory-check.yml` for that PR, branch and SHA passed its `memory-check` job, and every `memory-check` check run on the SHA, superseded ones included, is one of that run's jobs by id. Belonging to the run's check suite isn't enough, since a workflow can post a check run into another run's suite. A `memory-check` from anywhere else closes the PR. For the same reason Kin doesn't use GitHub's auto-merge. Never grant the Kin App Workflows permission on this repo.

### Before switching it on

The memory mode is tested only against a fake GitHub. In memory mode on a scratch repo, check:

- [ ] A PR that touches only `journal/` shows `mergeable_state: "clean"` once `memory-check` passes, with no review.
- [ ] A PR that touches `decisions/` shows `blocked` until the owner approves.
- [ ] After the owner approves, a bot push that changes `decisions/` dismisses the approval.
- [ ] A rename from `decisions/x.md` into `journal/` stays gated on the owner's review.

## Cost

Each run checks out `t3code` at the pinned commit without `.repos/`, installs the server's dependencies with `vp install --frozen-lockfile --ignore-scripts --filter=t3...` and runs the lint with Node. The install dominates: 881 packages, which took 19 s from an empty store on a fast connection, so budget about a minute per run on a hosted runner, plus Vite+ and Node setup. Nothing is cached between runs, so a PR can't seed a cache the check later trusts. Gitleaks is a 7 MB release binary, checked against its sha256 before it runs, and scans the tree plus the new commits in seconds.

## Things to know

- GitHub runs a PR's own copy of this workflow, so a PR could rewrite the check. The `*` line in `CODEOWNERS`, which also covers `.github/`, is what stops that: such a PR needs the owner's review. A ruleset `workflows` rule isn't available on a user-owned repo, so Kin checks the check's workflow and SHA itself before merging (see Workflow permissions above).
- A `.gitleaksignore` anywhere in the memory repo fails the check, because gitleaks would honour it. `gitleaks:allow` comments are ignored.
- A false positive the owner allowed in `kin_secret_allow` still fails gitleaks, which has no allowlist. Reword the text; whether the owner may merge past the check is settled with the ruleset.
- `CODEOWNERS` denies by default, so a new root file such as `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.mcp.json` or `.codex/` needs the owner's review before the lead's read checkout loads it. The lint fails if the file still names `@OWNER` or frees any path beyond Kin's own.
- CODEOWNERS can't carve a path back out of Kin's owner-less lines, so the lint does it: under those paths it allows only `commitments/`, `deferrals/` and `claims/` items one level deep (`<id>.md`, never an agent instruction file name such as `CLAUDE.md` or `AGENTS.md`), `journal/YYYY/MM-DD.md` and a root `INDEX.md` file. It reads git's index, so a `.claude/` folder, a symlink or a submodule fails it rather than being skipped; paths the owner reviews stay free-form.
- Gitleaks matches the scanner's patterns but not its Unicode folding, wrapped-token joining or word boundaries, so it can flag both more and less than the scanner. It adds its own decoding and covers every commit in the PR, merge resolutions included.
- Gitleaks scans file contents, not file paths. A token in a file or folder name passes this check; only `KinSecretScan` catches it, on Kin's own writes.
- Other known gitleaks misses, left as they are: a value an allowed `secret-assignment` match swallows (`secret=https://x/?db_password=…`, `token_scopes=read&api_key=…`), and a token split across lines or hidden with zero-width or fullwidth characters.
